# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

REST API backend for [Catalog.beer](https://catalog.beer), a beer database service. PHP-based API with no framework and no dependency manager (no Composer). Runs on Apache with mod_rewrite. Integration tests run via Newman (Postman CLI).

Related repos:
- Frontend: [catalog-beer](https://github.com/michaelkirkpatrick/catalog-beer)
- Database schema (canonical): [catalog-beer-mysql](https://github.com/michaelkirkpatrick/catalog-beer-mysql)

API documentation page (for external consumers) lives in the frontend repo: `../catalog-beer/api-docs.php`

## Repository Layout

The repo root mirrors the vhost root on the 26.04 servers (`/var/www/html/<vhost>/`), not the web root. Adopted 2026-09-25 for the Ubuntu 24.04 → 26.04 move (Linode repo: `Project-Conventions.md` § Secrets handling, `2604 Upgrade Plan.md` § Gap 4 and § Gap 5); `mekstudios.com` converted the same way a week earlier and is the reference.

```
catalog-beer-api/
├── public_html/      ← Apache DocumentRoot: index.php, errors.php, .htaccess, robots.txt, classes/
├── common/           ← secrets only: passwords.php (gitignored) + Secrets.md
├── cron/             ← CLI scripts; deployed beside public_html/, never served
├── algolia/          ← CLI index tooling; deployed beside public_html/, never served
├── tests/            ← Newman collection + offline PHP tests; never deployed
├── tools/            ← build scripts for generated classes (build-telephone-metadata.py → TelephoneMetadata.class.php); never deployed
├── scratch/          ← local working files; gitignored AND rsync-excluded
├── deploy.sh, deploy.conf(.example), CLAUDE.md, README.md
```

`ROOT` is always `public_html` (from `$_SERVER['DOCUMENT_ROOT']` on the web, `dirname(__DIR__) . '/public_html'` in the cron, algolia and DB-backed test scripts), so `dirname(ROOT)` is the vhost root everywhere and the secrets load from `dirname(ROOT) . '/common/passwords.php'`. **Nothing under `public_html/` may ever be named `common/`** -- the legacy layout kept the secrets there, and `.gitignore` and `deploy.sh` both carry tripwires against it coming back.

`deploy.sh staging` ships the working tree; `deploy.sh production` ships `git archive HEAD` (only committed files can reach production; `--dirty` is the emergency escape). Both mirror `public_html/`, `cron/` and `algolia/` to the same names under the vhost root and refuse to run until `common/passwords.php` exists there. The secrets file is never deployed -- `common/Secrets.md` § Server layout has the one-time move for a 24.04 box and the install command for editing it on a server.

**PHP-FPM (26.04):** the API reads its key from `$_SERVER['PHP_AUTH_USER']`, and Apache strips the `Authorization` header from FastCGI backends unless `CGIPassAuth On` is set -- `public_html/.htaccess` carries it. Under mod_php it is a no-op, so a 24.04 box cannot reveal its absence; a 26.04 box answers 401 to every key.

## Development Environment

This is a plain PHP project served by Apache. There are no build steps, linters, or test runners. Development requires:
- Apache with mod_rewrite enabled
- PHP with mysqli extension
- MySQL database named `catalogbeer`

Environment comes from an exact hostname table in `public_html/classes/initialize.php`:
- `api-staging.catalog.beer` → staging
- `api.catalog.beer` → production
- anything else → 421 before secrets load (exit 1 under the CLI); it never falls through to production. Apache's catch-all vhost denies unknown hosts first, so tripping this means a vhost gained a name without a row.

## Architecture

### Request Flow
1. `public_html/.htaccess` rewrites all URLs to `index.php` with query parameters (`endpoint`, `id`, `function`)
2. `public_html/classes/initialize.php` bootstraps: constants, timezone (`America/Los_Angeles`), SPL autoloader
3. `index.php` parses JSON body, validates headers (Content-Type, Accept), authenticates via HTTP Basic Auth (API key as username)
4. `switch($endpoint)` routes to the appropriate class, calling its `api()` method
5. Class sets `$responseCode`, `$responseHeader`, `$json`; `index.php` outputs the JSON response
6. Request is logged via `apiLogging` (except for master API keys)

### Class Autoloading
SPL autoloader in `initialize.php` loads `ROOT . '/classes/{ClassName}.class.php'` (i.e. `public_html/classes/`). All class files follow this naming convention.

### Entity Class Pattern
Entity classes (`Beer`, `Brewer`, `Location`, `Users`) share a consistent structure:

**Properties:**
- Entity fields (e.g., `$brewerID`, `$name`)
- Error state: `$error` (bool), `$errorMsg` (string), `$validState` (bool), `$validMsg` (string array)
- Response: `$responseCode` (int), `$responseHeader` (string), `$json` (array)
- Cache: `$brewerObj` (cached Brewer for reuse), `$totalCount` (cached count for pagination)

**Methods:**
- `api($method, $function, $id, $apiKey, ...)` — Main router; switches on HTTP method and `$function`
- `add($method, $id, $apiKey, $data)` — Handles POST, PUT, and PATCH in a single method with `switch($method)` to vary required fields
- `validate($id, $saveToClass)` — Checks if entity exists by UUID; if `$saveToClass` is true, populates class properties
- `delete($id, $userID)` — Soft or hard delete with permission checks
- `generateObject()` — Builds the JSON response object for the entity; accepts optional cached `$brewerObj` to avoid re-querying
- `generateSearchObject()` — Builds the Algolia search index object; accepts optional cached `$brewerObj`

**Query optimization patterns used in `add()`:**
- PUT calls `validate($id, true)` to populate class properties, then saves original values (`$originalCBV`, `$originalBV`, etc.) before they're overwritten — avoids redundant `SELECT` queries for brewerID, cbVerified, brewerVerified
- The validated `$brewer` object is cached in `$this->brewerObj` and reused by `generateObject()`/`generateSearchObject()`
- `Privileges::brewerList($userID)` assumes the caller has already validated the userID
- `Location::validate()` reads the address columns and JOINs `subdivisions` for the region's name and type in one query

### Verification & Permissions
Two badges; only one of them restricts editing:
- **cbVerified** — Catalog.beer admin reviewed the record. **An indicator, not a gate** (since 2026-10-13): any account may edit a cb_verified brewer, beer, location or address. Admin writes set it (except an admin URL-only brewer PATCH, which carries both badges through); **any non-admin write clears it**, so the badge always describes content an admin has seen. Address writes clear it on the parent location via `Location::updateLastModified($id, true)`. The old 403 error numbers 161/166/185/191 are retired, not reused.
- **brewerVerified** — Brewery staff verified; **still a gate**: only that brewery's staff or admins can edit (errors 168/186/187/192). It is the stronger claim of the two, since the brewery itself vouched for the record. `GET /brewer/{id}/permissions` reports `edit` from this flag alone.

Deletes are a separate rule and do not depend on either badge: admins and brewery staff only.

Staff status determined by: user email domain matching brewer's `domainName`, or explicit entry in `privileges` table. Admin status is a flag on the user account.

**Brewer URLs: one brewer per homepage, not one per domain** (since v4.1.0, 2026-09-24). `brewer.domainName` is the URL's host, `www.` stripped and lowercased; it is indexed but **not unique**. A domain's root URL belongs to at most one brewer and no two brewers may hold the same page, but any number may hold distinct sub-pages of one domain — an acquired brand that carries on under its own name lives on a page of its owner's site (Whetstone Beer Co. at `northchair.com/whetstone-beer/`) beside the owner's record at the root. `BrewerUrl.class.php` is the one place host and page keys are computed: `host()`, `path()`, `pageKey()` (trailing slash and `/index.html` collapsed, case-insensitive, fragment dropped, query kept), `isRoot()`, and `conflict()`, which classifies every brewer on the host and returns the colliding row with `match: root|page`. `Brewer::validateURL()` calls it (error 182, two messages) after `UrlCheck` has canonicalized the URL; `unique_url` remains as the byte-identical backstop. Because staff rights come from the email-domain match, **a shared domain shares staff by design** — an `@owner.com` address is staff on every brewer that stores `owner.com`. **Offline regression test: `php tests/brewer-url.php`**; `conflict()` is covered by `tests/brewer-lead.php` and the Postman "Shared Domain" folder (BR-238..245).

**Brewer status, operating years and country** (since v5.3.0, 2026-10-05). `brewer.status` (`active`|`closed`), `foundedYear`/`closedYear` (year-only, `smallint`) and `countryCode` (ISO 3166-1 alpha-2, default `US`, the standard `location.countryCode` already used) ride on every brewer object as `status`, `founded_year`, `closed_year`, `country_code` — including the hand-built embeds in `Brewer::search()`, `Beer::search()`, `Location::nearbyLatLng()` and `Review::claim()`. **`status` is the authoritative flag**: a closure whose year is unknown is `closed` with a null year, so the flag is never derived from the year. `closed_year` needs `status: closed` and cannot precede `founded_year` (errors 329–333; the schema's two `CHECK` constraints are the backstop); a PATCH back to `active` clears a stored `closed_year` the request did not address. **PUT omits → defaults** (active, null, null, US), the REST contract, so a PUT from a client that predates the fields reopens a closed brewer — the frontend form PATCHes, and the skill says to. Any key may set any assigned `country_code` (decided 2026-10-06: a gate would only guarantee wrong data, since a form with no option stamps every brewer US; locations stay US-only and the review loop still skips non-US brewers for research); error 335 is freed; `CountryCode.class.php` holds the 249 assigned codes with ISO short names (**offline test: `php tests/country-code.php`**). What reads the flag: `Location::add()` refuses a new location, or one being moved, onto a closed brewer (400 on `brewer_id`, error 336 — the map and `/location/nearby` read the location table directly, and a closed brewery's locations are deleted on a human decision, so this is what keeps a stale page from putting one back); `cron/check-urls.php` only checks active brewers; `/brewer/search` orders closed below active within a tier; `Review::claim()`'s queue skips closed brewers (a named claim still holds one, which is how a mistaken closure is undone); Algolia brewer records carry `status` and `country_code` as facets (`php algolia/settings.php` pushes the setting); `snapshot-metrics` records `brewer_status` and `brewer_country` (grouped) and `brewer_with_founded_year`. **Leads:** `POST /brewer-lead` takes `country_code` (default `US`); a non-US lead needs only `city` + `country_code` to be placed (`sub_code` is then shape-checked and must share the country), dedups by name within the country, **is never handed out by the queue** (a named claim still works) and is listed with `GET /brewer-lead?country_code=XX` — the open non-US leads are the expansion backlog, which is why a non-US discovery is filed instead of thrown away. `sub_code` is `varchar(6)` in all three tables (`GB-ENG`). Schema: `catalog-beer-mysql/migrations/2026-10-05-brewer-status-country.sql`. Postman folder "Brewer Status" (BR-256..266 + L-180); `tests/review.php` and `tests/brewer-lead.php` cover the queue rules.

### International addresses

**The address lives on the location row** (since v6.0.0, 2026-10-17): ten nullable columns on `location` — `line1`, `line2`, `locality`, `dependentLocality`, `sub_code`, `postalCode`, `formatted`, `languageCode`, `telephone`, `validatedAt` — NULL as a block when the location has none. Before that, `USAddresses` and a `US_addresses` table (US only), then for four days a one-table-for-every-country `address` keyed by the location's id, which was a 1:1 row, not a relationship: it cost a denormalized country that had to be guarded, a JOIN in every read, and a second write request that could fail after the first succeeded (the frontend held a "pending location" in the session to survive that). **The address is written as a nested `address` object on POST/PUT/PATCH `/location`, and it is required** (since 2026-10-20: it was optional only while it took a second request): POST and PUT without one, or with `"address": null`, are validated as an empty address, so the 400 names the fields the country needs (`error_msg` "Every location needs its address"); PATCH may omit it (kept) but `"address": null` is refused (error 345) — an address is corrected, never removed. It is validated BEFORE the row is written, so a refused address writes nothing and no location is created or replaced without one. PATCH merges the nested fields over the stored ones (a telephone-only patch skips Google; `locality`+`sub_code` and `postal_code` are two spellings of one place, so patching one group drops the other to be re-derived); PUT replaces (omitted sub-fields clear). Locations that predate the rule and hold no address still read (the all-null block) and PATCH without one. `valid_state`/`valid_msg` nest an `address` object with the seven keys (always present). The address's country is **the location's `country_code`, never a field of its own**; changing the country of a location that holds an address without re-sending the address is refused (341) — send it again and it re-validates under the new country. `Address.class.php` is the validator (`validateFor()` → `columns()` / `coordinates()`), the parsers and the wire shape (`loadRow()`/`toArray()`/`wireObject()`); it owns no table. Retired error numbers: 57, 66, 183, 189, 190; new: 344 (`address` not an object), 345 (PATCH removing the address). `Location::validateCC()` accepts any code in `Address::COUNTRIES` — the 40 regions Google Address Validation covers (AR AT AU BE BG BR CA CH CL CO CZ DE DK EE ES FI FR GB HR HU IE IN IT JP LT LU LV MX MY NL NO NZ PL PR PT SE SG SI SK US) — with two messages on error 51 (not a country; a country not yet supported), so an address never has to degrade. (A `validation` state column was built and dropped the same week: every address goes through the validator, so it could only ever read `validated`.) `country_short_name` everywhere is `CountryCode::shortName()`.

**One vocabulary, a MAJOR bump.** The nested `address` takes `line1` (street), `line2` (unit), `locality`, `dependent_locality`, `sub_code`, `postal_code`, `telephone`; `valid_state`/`valid_msg` carry exactly those seven keys. Every address object (`GET /location/{id}`, `/brewer/{id}/locations`, `/location/nearby`, the search object) carries those plus `formatted` (array of display lines in the country's own order, country name excluded), `language_code` and `admin_area` (`{sub_code, name, type}` or null) — ten keys, built by `Address::wireObject()`/`toArray()`, the one shape builder. **The pre-6.0 shape is gone**: `address2`/`address1` (USPS order, the street second), `city`, `zip5`/`zip4`, `state_short`/`state_long`, the top-level `telephone` on nearby rows, and the `zip_code`/`state` query aliases. Unknown body keys are ignored, so an old client gets the "missing the street address" 400, never a partial write. Decided 2026-10-13 after `api_logging` (back to 1 July) showed no external key had ever written an address — every non-admin write was the Newman suite — and the dozen external readers of `/brewer/{id}/locations` were hobby-volume; the alternative, a dual vocabulary carried as a deprecation window, was built first and then stripped the same day. The frontend therefore ships in the same deploy window as the API. **`telephone` is an E.164 string (`"+15035550100"`)**, where it was an int. `Address::normalizeTelephone()` reads international (`+`, `00`, NANP `011`) or national forms using the location's country for the calling code and trunk prefix (Italy keeps its 0; see `TRUNK_PREFIX`). **Every address object also carries `telephone_formatted` and `telephone_national`** (since 2026-10-20): the same number grouped the way its country writes it (`+31 20 528 6237` / `020 528 6237`), computed on read by `Telephone.class.php` from `TelephoneMetadata.class.php` — a GENERATED table of per-country formats and lengths, extracted from libphonenumber's `PhoneNumberMetadata.xml` (Apache 2.0) by `tools/build-telephone-metadata.py` for the 40 `Address::COUNTRIES`; rebuild it from a newer release rather than editing it. The matcher is ours. The only validity check it adds is length: a national number of a length its country never issues is refused (error 346); the full per-type patterns are deliberately not enforced, so a stale table can't refuse a real number. Test: `php tests/telephone.php` (expected layouts are each country's convention, checked by a person).

**Validation flow:** `regionCode` is the location's country and `enableUspsCass` only for US/PR. The acceptance gate is shared — building-level granularity, or in the US a USPS DPV confirmation — and so is `relocationConflict()`. Then two parsers: **US** keeps `parseValidatedAddress()` + `deriveCity()` and the CASS-vs-Google rules untouched (`tests/address-parse.php`, 51 fixtures); **every other country** is `parseInternational()`, where Google's rendering is the truth: `line1` is `postalAddress.addressLines[0]` with the postal abbreviation undone from the route component via `expandPostalLine()` ("Köpenicker Str." → "Köpenicker Straße", "Bd" → "Boulevard"), `line2` the subpremise cut out of the line when Google folded it in ("Meir 85/bus 3"), `locality` is `postalAddress.locality` (Google already resolves Westvleteren vs Vleteren and London vs postal_town), `formatted` is `formattedAddress` split on `", "` with the country dropped and a North-American "City, ST postal" line rejoined. `sub_code` outside the US comes from `Subdivisions::lookup()` over Google's administrative areas (ISO suffix or name, accent-insensitive via the collation) — Google wins over a client-sent code, no match keeps the client's, neither is NULL, **never a 400**: Belgium returns no province at all. Fixtures: `tests/fixtures/google-address-validation-intl.json` (22 real responses captured 2026-10-13 from the staging box, since the key is IP-restricted); the probe script shape is in that file's `request` keys. Errors: 337 country not in the list (unreachable via the location gate), 338 sub_code in another country, 339 postal-code shape (`POSTAL_SHAPES`, loose, pre-flight only — Google's answer is what is stored), 340 international completeness, 341 country change without the address, 342 bad `country` on `/location/subdivisions`, 343 bad `country` on nearby, 344 `address` not an object, 345 PATCH `"address": null` (removing a required address). The US ZIP errors 59/60 now blame `postal_code` (`97201` or `97201-1234`); 61 asks for a locality or a postal code.

**Subdivisions** are seeded from ISO 3166-2 for the 40 countries at the level Google reports as an administrative area (1,082 rows + the 51 US; Belgium gets regions AND provinces, Spain/Italy both levels, GB its four countries), with `countryCode`, `sub_type` and `parentCode`; names are the local official form. `BrewerLead` validates a lead's `sub_code` against the seed whenever the country has rows. **Nearby:** `/location/zip` takes `postal_code` + `country`, `/location/city` takes `city` + `country` + `region` (required only for the US); `metric` defaults to kilometers outside US/LR/MM. **Algolia:** location records carry `address.line1`, `line2`, `locality`, `sub_code`, `postal_code` and a `regions` facet (ISO 3166-2) beside `states` (bare US code, kept for the search page's facet UI); brewers and beers carry `regions` through `locationFacets()` → `searchGeography()` → `cascadeGeographyToBeers()`, which now sends four keys. Push `php algolia/settings.php`, then re-save records. **Metrics:** `location_with_address` counts locations with a street; `location_country` is a new grouped series. **Tests:** `php tests/address-parse.php` (US + international fixtures, telephone normalization), `php tests/address.php` (local MySQL: both migrations' data statements replayed, the nested writes, clearing, the location gate), Postman folder "International Addresses"; the former `/address` tests (A-N) now run as `PATCH /location` with a nested address. ### Pagination
Uses base64-encoded cursor pagination. Default count is 500 per page. Cursor is base64 of the offset number. Count queries are cached in `$this->totalCount` to avoid duplicate `COUNT` calls between validation and `nextCursor()`. `Location::nearbyLatLng()`, `Beer::search()`, and `Brewer::search()` use a `LIMIT count+1` approach instead of a separate count query — if the extra row is returned, there are more results.

**`modified_since` — the incremental-sync filter** (since 6.1.0, 2026-10-20). `GET /brewer`, `/beer` and `/location` take `?modified_since=<unix seconds>` and return only rows with `lastModified >= ?`, so a client that mirrors the catalog fetches what changed instead of re-listing everything. Inclusive on purpose (a write in the same second as the client's clock reading is caught; a duplicate costs a sync nothing, a miss is a stale record forever). The count query and the cursor range run over the filtered set — `countBrewers($modifiedSince)` and friends — and **`nextCursor()` must receive the value too**, or an empty filtered page falls back to the whole table's count and claims a next page. The response echoes `modified_since` when the filter is on. Anything but 1–10 ASCII digits (the empty string, a sign, a decimal, an array) is a 400 (errors 356/357/358; `modifiedSince()` in each class), so a client with a broken variable never downloads the whole catalog. **Deletes are not reported** — entities are hard-deleted with no tombstone, so a 404 on the entity is the only signal; the docs say so. Index: `idx_{brewer,beer,location}_lastModified` (`catalog-beer-mysql/migrations/2026-10-20-last-modified-index.sql`). **Offline regression test: `php tests/modified-since.php`** (local MySQL, scratch `cb_modified_since_test`; also asserts the canonical schema carries the index). Postman folder "Modified Since" (BR-271..278, BEER-181..183, L-193..195, Brewery #59).

### Text Input Validation
`TextInput.class.php` is the single shape check for user-submitted free text, called from the `validate*()` methods of `Brewer`, `Beer`, `Location` and `Users` (9 sites, all logging error number 305). Each validator keeps its own error number and per-field message for length and required-ness — `TextInput` only answers "may these characters be stored at all."

**The rule: store raw bytes, escape at the point of output, but reject characters that have no visual form and exist only to steer a parser.** `index.php` 400s *raw* control bytes via `JSON_ERROR_CTRL_CHAR`, but the JSON-*escaped* forms (`\u0000`, `\u2028`, bidi overrides) are valid JSON and used to land in the column intact.

- `TextInput::trim($v)` — `trim()` widened to Unicode: strips `\p{Z}`, NBSP, ZWSP, LRM/RLM and BOM from both ends. Because `\p{Z}` covers `U+2028`/`U+2029`, a value whose only problem is a trailing line separator is *cleaned* rather than rejected.
- `TextInput::check($v, $allowNewlines = false)` — returns `''` when storable, else a ready-to-show message. Rejects C0 except LF/CR, plus DEL, TAB, `U+2028`/`U+2029` and bidi overrides (`U+202A-202E`, `U+2066-2069`). With `$allowNewlines = false` (names, `style`, `short_description`, `url_note`) it also rejects LF/CR.

**Zero-width is trimmed at the edges, never rejected** — `U+200C` ZWNJ and `U+200D` ZWJ are required by Persian, Arabic and Indic scripts and by emoji sequences, so a blanket ban on the range would break legitimate international names.

**Offline regression test: `php tests/text-input.php`** — no DB, no network; includes the real production values that motivated each rule. Run it for any change to the character policy, and add a case before adding a rule.

**Sign-up abuse checks (`SignupGuard.class.php`, since 2026-10-29).** `POST /users` refuses a **disposable email domain** (400 on `email`, error 359) — the address's domain or any parent of it on the vendored `classes/resources/disposable-email-domains.txt`, a byte copy of `disposable_email_blocklist.conf` from https://github.com/disposable-email-domains/disposable-email-domains (CC0, ~10k domains; refresh by re-downloading, never hand-edit). The check sits in `Users::validateEmail()`, so a PATCH that changes the email is screened too. When the frontend sends the visitor's address as `signup_ip`, the row stores `createdAt`, `signupIP` and `signupNet` (the IPv4, or the IPv6 /64 — `SignupGuard::network()`), and two caps apply, both 429 with an `error_msg` the form shows: **3 accounts per network per day** (error 360) and **10 website sign-ups per hour site-wide** (error 361). Rows without a `signupNet` (Newman, scripts, every account before the migration) are neither counted nor capped, so the suite's three `POST /users` can never trip the breaker. A missing list fails open and logs 362. Why: on 2026-10-29 one person opened nine accounts in two days (seven in fourteen minutes) from temp-mail domains, verified each from the throwaway inbox and burned every key's 1,000 free requests dumping `/brewer/{id}/beer`; reCAPTCHA on the site passed all of them. **Offline regression test: `php tests/signup-guard.php`** (the real domains from that wave, so a refreshed list that drops one fails loudly). Schema: `catalog-beer-mysql/migrations/2026-10-29-users-signup-provenance.sql`, run **before** this deploys (the INSERT names the columns).

### Request logging (`api_logging`)
`apiLogging::add()` writes one row per authenticated request (master keys, `/usage` and `/billing` excepted) and `Usage::pruneLogging()` deletes rows older than 3 months, so the table is a rolling window, not history; `api_usage` keeps the monthly counts billing needs. **A successful write stores only a stub of its response** (since 2026-10-29): `apiLogging::responseStub()` keeps `id`, `name` and the nested `brewer`'s `id`/`name` — exactly what `/activity`'s Recent Activity reads back — and drops the rest; GETs store no response, and a 4xx/5xx keeps the scrubbed error body (small, and the only record of why a caller's write was refused). Before this the full entity rode on every write and two bulk-load months of `POST /beer` put 156 MB into a 488 MB table on a box whose buffer pool is 128 MB. Offline test: `php tests/api-logging-stub.php`. The log is not an audit trail — see `Claude Ideas/audit-log.md`.

### Error Logging
All errors are logged to the `error_log` database table via `LogError` class. Each error site has a unique `errorNumber`. **Re-grep for the current maximum rather than trusting any written figure** — `grep -rhoE "errorNumber *= *[0-9]+" public_html/ cron/ algolia/ | grep -oE "[0-9]+" | sort -n | uniq | tail -5`. Note `errors.php` deliberately uses 405/500/503 as HTTP-status-shaped error numbers, which are not part of the sequential range. When adding new error logging, use the next available error number. `LogError::write()` has a static recursion guard (`self::$writing`) to prevent infinite loops when the database is down. CLI-safe: uses null coalescing for `$_SERVER['REQUEST_URI']` and `$_SERVER['REMOTE_ADDR']`.

### Database Access
`Database.class.php` wraps mysqli with prepared statements. Key methods:
- `query(string $sql, array $params = []): ?mysqli_result` — Prepare and execute a query with `?` placeholders; auto-detects param types (`i` for int, `d` for float, `s` for string); returns `mysqli_result` or `null` on error
- `getInsertId(): int` — Returns the last insert ID
- `getConnection(): mysqli` — Returns the underlying mysqli connection
- `close()` — Closes the database connection

All queries use parameterized `?` placeholders. Database credentials are loaded from `common/passwords.php` (gitignored) via constants `DB_HOST`, `DB_USER`, `DB_NAME`, `DB_PASSWORD`.

**Query patterns:**
- Single row: `$result = $db->query("SELECT ... WHERE id=?", [$id]); $row = $result->fetch_assoc();`
- Loop: `$result = $db->query("SELECT ..."); while($row = $result->fetch_assoc()) { ... }`
- INSERT/UPDATE/DELETE: `$db->query("INSERT INTO t (...) VALUES (?, ?)", [$a, $b]);`
- Dynamic PATCH: Build `$setClauses[]` and `$setParams[]` parallel arrays, then `implode(', ', $setClauses)`
- PUT full replacement: Optional fields use `if(!empty()) { $setClauses[] = 'col=?'; } else { $setClauses[] = 'col=NULL'; }` — omitted fields are cleared per REST standards
- Optional INSERT fields: Build `$columns[]` and `$params[]` arrays, add optional fields conditionally
- JOINs: Used where related data is needed together (e.g., `Location::nearbyLatLng()` JOINs location+brewer+subdivisions)
- FULLTEXT search: `Beer::search()` and `Brewer::search()` rank in tiers — exact name, all query terms in the name as word prefixes (BOOLEAN MODE against a name-only FULLTEXT index), then the blended `NATURAL LANGUAGE MODE` match — so name matches always outrank description/style mentions. Query strings are sanitized by `SearchQuery::terms()` (`SearchQuery.class.php`), which strips FULLTEXT operator characters (a bare `*` is a parser error even in natural-language mode) and removes InnoDB stopwords from the boolean query (a required stopword like `+the*` silently matches nothing). `Beer::search()` JOINs with brewer to return full objects in one query

## Database Schema — keep `catalog-beer-mysql` in sync

The canonical DB schema is a **separate, public repo**: [catalog-beer-mysql](https://github.com/michaelkirkpatrick/catalog-beer-mysql) (`catalog-beer-schema.sql`) — declarative DDL for the whole `catalogbeer` database. The live migration DDL (the style taxonomy system + `beer` column additions) is authored in `style-library/scripts/migration/` (`01_migration.sql`, regenerated `02_seed.sql`, and the `staging-sync-*.sql` upgrades for already-migrated DBs).

**When you add or alter any table or column — in a migration, or directly in this API — update `catalog-beer-schema.sql` in the SAME change** so the canonical schema never lags, and bump its git tag (`v2.x`; check `git tag | sort -V | tail -1`). It's easy to forget: it lives in a third repo, isn't imported by the app, and nothing breaks if it's wrong — but it is the schema every human and every future Claude session reads as truth.

Touchpoints here that imply a schema change: a new entry in an entity's `$columns[]`/`$setClauses[]` arrays in `add()`, a new `CREATE TABLE`, a new index, or a `SELECT` that reads a column that doesn't exist yet (e.g. the `style_confidence` column added for the Guided Style Field).

## API Endpoints

Defined in `public_html/.htaccess`. All IDs are 36-character UUIDs:
- `/activity` — Admin-only activity report (`Activity.class.php`); queries `api_logging` for write summary, top contributors, recent activity, GET traffic
- `/brewer`, `/brewer/{id}`, `/brewer/{id}/beer`, `/brewer/{id}/locations`, `/brewer/count`, `/brewer/search`
  - `/brewer/{id}/beer` has **no default cap** (48 brewers hold more than 500 beers; the brewer page renders the whole list) and takes optional `?parent=` (family slug), `?exclude=` (a beer_id) and `?count=` (1..500, `LIMIT count+1` sets `has_more`), each a 400 when malformed (errors 326-328) so a typo never returns the full catalog. Read from `$_GET` in `Brewer::api()`, not from index.php's `$count` (which defaults to 500 and cannot say "absent"). The beer page's "more from this brewer" strip is the consumer: six same-family siblings instead of the whole list (1.5 MB for the largest brewer). The rewrite rule carries `QSA`; most sibling rules do not, so a new query parameter on another route needs the flag added. Postman folder "Brewer Beer Filters" (BR-246..255).
- `/beer`, `/beer/{id}`, `/beer/count`, `/beer/search`
- `/billing` (GET status / PATCH spend cap / DELETE disable), `/billing/checkout-session`, `/billing/portal-session` — Stripe usage billing (`Billing.class.php`); exempt from the rate-limit gate and from api_logging/api_usage counting so a capped key can still manage billing
- `/stripe-webhook` — POST-only, no Basic Auth (verified by Stripe webhook signature instead); routed before header/auth checks like `/health`
- `/location/{id}`, `/location/nearby`, `/location/map` (admin-only, all locations with coordinates for map display)
- `/location/countries` (GET: the countries a location may be in, with a subdivision count and calling code each), `/location/subdivisions?country=XX` (GET: the seeded ISO 3166-2 rows). **There is no `/address` endpoint since 6.0** — the address is a nested object on the location's own writes; `/address/*` answers 404 with a pointer.
- `/users/{id}`, `/users/{id}/api-key`, `/users/verify-email/{id}`, `/users/{id}/reset-password`, `/users/password-reset/{id}` — `POST /users` is admin-only and takes an optional `signup_ip` (see § Sign-up abuse checks)
- `/login`
- **No `/review` or `/brewer-lead` since 6.3.0 (2026-10-23).** The brewer review loop's queue, claims, records, leads and questions moved to their own service, `review.catalog.beer` (repo `catalog-beer-review`, design in `../Claude Ideas/review-service.md`), which forwards catalog calls through `/catalog/*` with a dedicated admin key. The retired routes answer 404. Error numbers 310–325 and the other numbers those two classes used are retired, not reused. The URL-health columns on `brewer` and `cron/check-urls.php` remain only until the service's URL audit has worked through its seed; then they go too.
- `/post` (GET, POST), `/post/{id}` (GET, PATCH, DELETE), `/post/{channel}/{slug}` (GET) — The frontend's `/news` announcements (`channel: news`) and the API changelog at `/changelog` (`channel: api`, one post per release of this repo) (`Post.class.php`). **Reads are open to any key; writes are admin-only** (401, error 350). An admin is any key whose account carries the admin flag, **master keys included** (until 2026-10-21 they were refused, which locked the master-key account out of `/admin/posts`). A draft is returned only to an admin who asks for it with `?status=all` or `?status=draft` — by id, by slug and in the list — so a read without `status=` is a public read whatever the key, and the website's master-key pages can never render one; `GET /post?status=draft|all` from a non-admin is a 403. Writes see drafts regardless (`get(..., $includeDrafts)`). The list is newest first by `published_at`, filters with `?channel=`, defaults to 20 per page (max 100) and uses `LIMIT count+1` for `has_more`. Only `api` posts carry `version` (5.4.0, 2.1, 2.0-beta.1; a leading `v` is dropped) and `breaking`, and `version` is required there. `slug` defaults to `v{version}` for a release and to the slugified title for news; dots are allowed so a release reads `v5.4.0`. Duplicate slugs within a channel and duplicate versions are 409s naming the field. `published_at` is the date readers see, separate from `created_at`, so a release can be back-dated to its push; publishing without one stamps now, and a published post cannot clear it. `channel` is fixed after create. PATCH keeps absent fields; `summary: null` clears it. **`body` is admin-authored Markdown (raw HTML allowed) that the frontend renders with vendored Parsedown and emits** — the API stores and returns it as written; posts from before 2026-10-21 are plain HTML and render unchanged. The admin-only write is the whole trust boundary, so never open writes to non-admins without adding a sanitizer. Every object carries `url`, the page on the site. Errors 350–355. Schema: `catalog-beer-mysql/migrations/2026-10-17-post.sql`, minus `authorUserID` (`2026-10-21-drop-post-author.sql`, run **after** the API deploy — nothing read it). **Regression test: `php tests/post.php`** — local MySQL, scratch `cb_post_test` database from the canonical schema. **When you tag a release, draft its changelog post**: `POST /post` with `channel: api`, `status: draft` and `published_at` set to the push time, written for API consumers from the commit range (not copied from the tag message, which is written for engineers); admin-only routes go in an *Internal* line. Michael publishes it from `/admin/posts`.
- `/metrics` — Admin-only catalog health metrics feed (`MetricsReport.class.php`); serves `metrics_daily` as chartable series, split into `history` (backfilled `total_*`/`created_*`, to 2017) and `live` (everything, from the first snapshot) — the two regimes must never be mixed
- `/usage`, `/usage/my-usage` — no response anywhere carries an API key: `/usage/my-usage` and `/billing` don't echo the caller's own (it authenticated with it; echoing it only creates a leak path when agents print responses), and the admin list `GET /usage` identifies each key by `user_id` + `api_key_last4` (the frontend's `admin/usage.php` groups on that pair)
- `/health` — Unauthenticated GET-only health check; returns `{"status":"ok"}` (200) or `{"status":"error"}` (503). Verifies Apache + PHP + MySQL. No logging. Used by exit1.dev for uptime monitoring.

## External Services

- **USPS Addresses API v3** — Address validation (`USAddresses.class.php`); OAuth 2.0 via `USPSAuth.class.php` using `USPS_CLIENT_ID`, `USPS_CLIENT_SECRET`, `USPS_API_BASE_URL` constants
- **Google Address Validation API** — Address verification + lat/lng (`Address.class.php`, every country in `Address::COUNTRIES`); API key via `GOOGLE_ADDRESS_VALIDATION_KEY` constant. The same constant currently also powers the legacy Maps Geocoding/Places calls in `Location.class.php` — still live for `/location/zip` and `/location/city` geocoding (now with `components=country:XX`), but no longer called from the address flow. US street/unit parsing is `Address::parseValidatedAddress()` (pure static); the rest of the world is `Address::parseInternational()` (see § International addresses). **The governing rule: USPS owns the street's STRUCTURE, Google owns the NAME's spelling.** `streetSkeleton()` reduces a street to its directionals + type; same skeleton means the sources differ only in spelling and Google wins ("COMRCL CTR BLVD" → "Commercial Center Boulevard", "SUB ZERO" → "Sub-Zero", "MCMURRAY" → "McMurray"), a different skeleton means CASS wins — Google's road data drops/adds directionals in ways that change where mail goes. CASS also wins for road *designations* (route contains a bare number: "West Arizona 92", "Farm to Market Road 423") and for streets Google returns *truncated* (route "India" for India St, marked CONFIRMED with no signal). Whether a unit exists is Google's `subpremise`, but CASS renders it ("Suite 12" in, "BLDG 12" out) and is trusted outright when Google reports no subpremise at all. Display form via AP-style `apAbbreviate()` ("4th St NW", "I-35") — its recognition of directionals/types is deliberately form-agnostic, since it sees both Google's spelled-out text and CASS's abbreviated text. **Offline regression test: `php tests/address-parse.php`** replays real captured responses (`tests/fixtures/google-address-validation.json`) — run it for any change to address parsing, and add a hand-verified fixture for any new shape encountered
- **Algolia** — Search indexing; API keys via `ALGOLIA_APPLICATION_ID`, `ALGOLIA_SEARCH_API_KEY`, `ALGOLIA_WRITE_API_KEY` constants (plain strings, not `getenv()`)
- **Stripe** — Usage billing (`Stripe.class.php` raw-cURL client, `Billing.class.php` logic; no SDK). Keys with a card on file (`api_keys.billingEnabled`) may exceed the free tier at $1 per 1,000 requests (blocks rounded up, clamped to `api_keys.monthlySpendCapCents`, default $50). Metering stays local in `api_usage`; Stripe only stores cards (Checkout setup mode), creates monthly invoices (`cron/bill-usage.php`, $5 invoice floor with roll-forward in `billing_charges`), and reports payment outcomes (`POST /stripe-webhook`). **Who emails what** (since 2026-10-29): we send the notice on the 1st, the first-failure email and the billing-turned-off email (`invoice.marked_uncollectible`; a hand-voided invoice sends nothing) through Postmark via `SendEmail::billingEmail()` with Reply-To billing@catalog.beer, templates `classes/resources/email-billing-*.html` paired with `email-billing-head.html` (not the shared `email-head.html`); **Stripe sends the receipt** (Dashboard › Customer emails › Successful payments), and its own failed-payment email stays off so customers don't get two. A card saved with `cvc_check: fail` is not made the default and does not enable billing — the webhook emails the customer to add it again (error 364); a saved card is otherwise never refused for a wrong CVC. Webhook emails are best-effort (error 365) and never fail the webhook, or Stripe would redeliver. **Offline test: `php tests/billing-notice.php`** (charge arithmetic, floor, charge date, card label, notice alerts, invoice line; October 2026's real figures). Constants: `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET` (environment-conditional: staging uses test-mode keys)
- **Postmark** — Transactional email (`SendEmail.class.php`, `PostmarkSendEmail.class.php`); server token via `POSTMARK_SERVER_TOKEN` constant (environment-conditional: staging uses sandbox server)

All secrets are centralized in `common/passwords.php` (gitignored, never committed). This file is loaded by `public_html/classes/initialize.php` (via `dirname(ROOT)`, see § Repository Layout) after the `ENVIRONMENT` constant is set.

## Cron Jobs

The `cron/` directory contains scripts intended to run as scheduled tasks on the server, not via web requests.

**Schedules and operational notes live in the private Linode repo (`Linode/Cron-Jobs.md`), not here.** That file is the one to update when a schedule changes, and the one to read before picking a time — the production crontab is shared with every other site on the server, so a slot that looks free in this repo often isn't.

- `cron/update-usage.php` — Counts `api_logging` rows per API key per month and upserts into `api_usage`. Run via: `php cron/update-usage.php [staging|production]` (defaults to production). CLI-only; exits immediately if accessed via web.
- `cron/bill-usage.php` — Monthly Stripe billing in two phases (since November 2026). **`record` on the 1st** records last month's overage per billing-enabled key into `billing_charges` and emails each customer with an unbilled balance the exact amount, the card and the charge date (or that it rolls forward under the floor), stamping `noticeSentAt` so a re-run never resends. **`invoice` on the 4th** (`Billing::CHARGE_DAY`) invoices keys whose unbilled total has reached the $5 floor (waived when billing December) — **without** requiring `billingEnabled`, since announced usage isn't cancelled by turning billing off afterwards. Idempotent: `INSERT IGNORE` charge rows, per-cycle notice stamps, per-row invoice-item tracking, Stripe `Idempotency-Key` headers. Run via: `php cron/bill-usage.php staging|production record|invoice` — the phase is required. Schema: `catalog-beer-mysql/migrations/2026-10-29-billing-notice-sent.sql`, run **before** this deploys.
- `cron/snapshot-metrics.php` — Writes ~77 catalog-health metrics per day into `metrics_daily` (definitions in `classes/Metrics.class.php`). Verification flags, completeness and API demand have no history in the schema, so a day not snapshotted is lost. Stores raw counts only — composite "health scores" are computed at display time so the formula can change without invalidating stored history. Deletions are inferred by differencing against yesterday's snapshot, since entity deletes are hard deletes with no tombstone. See `Linode/Cron-Jobs.md` for the metric families.
- `cron/check-urls.php` — Brewer link-health monitor (`classes/UrlCheck.class.php` classifies; see `Linode/Cron-Jobs.md`). Report-only apart from promoting `http://` to the site's own `https://`. Two rules the API mirrors: **replacing** a brewer's `url` resets the five monitoring columns to baseline, while **clearing** it keeps them and stores the removed address in `brewer.urlLastKnown` — so a record can distinguish "no website" from "domain lapsed, don't go looking". (`brewer_url_history` and the write-only `url_note` field were retired on 2026-10-23 with the review service; site-wide history is the audit-log project.) **The review half of this feature is not in this repo** — turning `check-urls.log` into actual corrections lives in `../catalog-beer-cleanup/url-cleanup/` (moved out of `scratch/` on 2026-08-09), and its `RUNBOOK.md` is the procedure. Changes to `UrlCheck`'s verdicts should be reflected there, since the runbook's buckets are named after them. **Offline regression test: `php tests/url-check-name.php`** — no DB, no network; covers `nameInText()` and `stripOwnDomain()`, the "does this page name the brewery" test that decides whether an `ok` row is ever read by a human. A page's mentions of its own domain are stripped before matching (the domain comes from the URL under test, so it is circular evidence — a content farm titled `nextdoorbrewing.com` scored `ok` on the brand tokens `next` and `door` inside it), but the bare label is deliberately kept, since for a one-word brand the label is the name.
- `cron/backfill-metrics.php` — One-time replay of historical daily size/growth snapshots from the `createdAt` columns. Only that family is reconstructable; verification, completeness and freshness are current-state only and necessarily begin at the first live snapshot. Uses `INSERT IGNORE` so it can never overwrite a real snapshot.

The `cron/` directory is deployed by `deploy.sh` to the vhost-root `cron/` beside `public_html/` on the server, outside the DocumentRoot (crontab paths are `/var/www/html/api.catalog.beer/cron/...`). Each script has a CLI-only guard that exits immediately if accessed via a web request.

`deploy.sh` excludes `*.md` from deploys, so documentation never reaches a server. The two exceptions are `cron/error-context.md` and `cron/php-error-context.md`, which the digest crons read at runtime as Claude system prompts — they have explicit `--include` entries that must stay **above** the `*.md` exclude in the `EXCLUDES` array, since rsync takes the first matching rule.

## Algolia Batch Upload

`algolia/batch-upload.php` (deployed to the vhost-root `algolia/`, beside `public_html/`) — Full re-index of the Algolia `catalog` index: every brewer with its locations and beers, then the styles. One `Algolia::batchSave()` call per brewer (`updateObject`, an upsert, chunked at 1,000), so a run is ~6,700 requests, not one PUT per record; safe to re-run. Run via: `php batch-upload.php [staging|production] [limit]` (defaults to production). CLI-only; must be run on the server.

- **The Algolia `objectID` is the entity's own id** (since 2026-10-29): a beer, brewer or location is indexed under its UUID, a style under `style-<slug>`. UUIDs don't collide across types, so the combined index needs no separate key. Before that, each entity had a second random UUID kept in a local `algolia` table (209k rows, 81 MB, one lookup on every save and delete), which existed only to hold that indirection; `migrations/2026-10-29-drop-algolia-table.sql` removes it **after** `batch-upload.php` has re-keyed the index and `algolia/delete-legacy-ids.php` has deleted the old records (that script reads the table, so it runs before the drop and goes with it). Real-time sync, the cascades and the brewer-delete fan-out all address records by entity id — `Brewer::childIds()` captures the children before the SQL delete cascades them away.
- Optional `limit` argument restricts number of brewers processed (for testing)
- **Staging and production share one Algolia application and the same `catalog` index.** `common/passwords.php` does not branch the Algolia constants on `ENVIRONMENT`, so every Algolia write from staging — the Newman suite's creates and deletes, `batch-upload.php staging`, settings pushes — lands in live search. Never rehearse a bulk Algolia script on staging; use the `limit` argument on production instead. (A `catalog_staging` index selected by environment is the fix, not yet built.)
- **Prose in a search object is capped at `Algolia::PROSE_MAX_BYTES` (3,000) by `Algolia::truncateProse()`** (brewer and beer `description`; UTF-8-safe, word-boundary, no mbstring). Algolia refuses a record over 10 KB and `saveObject()` only logs the refusal (error 228), so before this a brewer with a long description was stored and silently never indexed. **Offline test: `php tests/algolia-truncate.php`.** Pushing settings never re-indexes records; a new attribute needs every record re-saved (`batch-upload.php` rewrites everything).

**Schema dependency:** `update-usage.php` requires a `UNIQUE INDEX` on `api_usage (apiKey, year, month)` for `INSERT ... ON DUPLICATE KEY UPDATE`. The index must be applied before the cron runs:
```sql
ALTER TABLE api_usage ADD UNIQUE INDEX idx_apiKey_year_month (apiKey, year, month);
```

## Code Conventions

- 4 spaces for indentation
- Class files: `ClassName.class.php`
- Entity JSON uses `snake_case` keys (e.g., `brewer_id`, `error_msg`)
- PHP class properties use `camelCase` (e.g., `$brewerID`, `$errorMsg`)
- Database column names accessed via associative arrays using their SQL column names
- UUID generation via `uuid.class.php` (RFC 4122 v4, `random_bytes`-based, no DB uniqueness check needed)
